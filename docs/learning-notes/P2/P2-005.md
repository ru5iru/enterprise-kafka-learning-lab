## 1. Goal and context

Review type-safe in-memory data handling before streams, immutable events and concurrent work. Collection choice affects ordering, duplication and memory retention; it does not implement Kafka partition order or durable deduplication.

## 2. Concepts explained in my own words

List models positional sequence/duplicates, Set uniqueness by its contract, Map key-to-value association and Queue/Deque work ordering. Choose ArrayList for common indexed/sequential work; hash maps/sets require stable equals/hashCode keys and do not promise insertion order. Use an explicitly ordered implementation when order is part of a contract. Capacity and operation cost depend on implementation; avoid repeated linear lookup or unbounded retained data.

Generics catch incompatible values at compile time. List<Integer> is not a subtype of List<Number>. A producer parameter ? extends T supports reading T; a consumer ? super T supports writing T. Raw types/casts evade these checks and can move failure to runtime. Type erasure means arbitrary List<String> membership is not verified just by a runtime cast.

An unmodifiable wrapper reflects changes through its backing collection; List.copyOf makes an unmodifiable snapshot of references. Neither freezes mutable elements. List.of/copyOf reject null; do not assume every collection has the same null/duplicate policy.

## 4. Decisions and rationale

Use typed interfaces and contract-specific collection creation rather than raw types or blanket synchronization. Snapshot only where a stable boundary is needed; a live view can be valid when intentionally documented. Do not add a collection utility framework or global cache to the lab. No architecture decision changed.

## 5. Best practices and design patterns

Applies defensive copying, explicit collection contracts and producer/consumer generic bounds. These Java generic producers/consumers are not Kafka clients. Bounded caches/queues and durable idempotency are later engineering controls, not provided by a HashSet.

## 6. Common mistakes, errors and vulnerabilities

Mutable map keys can become unreachable under changed hashes; unbounded maps can retain data; unsynchronized collections can race. Reviewed these risks without inventing experiments. Observed wrapper aliasing and rejected snapshot mutation, duplicate factory input/null copy. Compiler rejected treating List<Integer> as List<Number>.

## 8. Debugging and operational notes

If a snapshot changes, inspect element aliasing as well as the container. If a key lookup fails, inspect key mutation and equals/hashCode. Do not rely on fail-fast iterators as a concurrency guarantee or suppress raw-type warnings to fix type design.

## 9. Security and SSDLC check

Keep synthetic IDs only. Input collection sizes and retained references are future resource-exhaustion concerns; generic types are not input validation or an authorization boundary. No secrets or persistent cache added. Deep copying/retention limits require context-specific later design.
