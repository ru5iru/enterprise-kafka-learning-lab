## 1. Goal and context

P1-034 makes tests observable after compiler setup, before CI. P1-033 is Done/pushed. The tests belong only to the tooling fixture, not a premature application.

## 2. Concepts explained in my own words

Surefire discovers unit tests in test; Failsafe runs integration tests after packaging and verifies their outcome at verify. A configured plugin or zero discovered tests is not a passing test suite. Report counts and nonzero failure propagation establish that the lifecycle actually executes assertions.

## 3. Work performed and artifact

Configured exact Surefire/Failsafe versions, distinct Test/IT includes and failIfNoTests, declared BOM-managed test-only JUnit, added one runtime-feature unit test and one JAR-bytecode integration test. Added controlled-negative gate script and updated module docs. Initial clean verify passed both real tests.

## 4. Decisions and rationale

Keep Failsafe execution on the actual child, avoiding a zero-test packaging=pom parent. Separate unit/integration phases and run verify to check integration results. Alternative skip/no-test green builds are rejected. Public probe-only expected values permit deterministic failure testing without poisoning source contracts.

## 5. Best practices and design patterns

Use test scope, explicit discovery, report-count assertions, bounded synthetic fixtures and restored state after negative checks. The packaged-artifact integration test spans compilation/packaging instead of merely duplicating a method unit assertion. No service integration pattern is implemented.

## 6. Common mistakes, errors and vulnerabilities

Misnamed tests can disappear, failIfNoTests omissions can hide that, and invoking integration-test alone can miss the final failure gate. Forced unit/missing/integration cases validate these risks. No disabled assertion/test skip was used to create green evidence.

## 7. Testing, verification and evidence

Initial clean verify ran exactly 1 unit and 1 integration test successfully. Final experiment observes expected assertion/discovery failures, checks XML failure counts and Failsafe verify execution, then restores reports to 1+1 with zero failures/errors/skips. Hosted CI remains not run.

## 8. Debugging and operational notes

When tests vanish, inspect suffixes/includes and provider rather than assuming success. For IT failure, run through verify and inspect generated failsafe reports. Restore default synthetic expectations and clean verify after a negative probe. Generated reports remain ignored.

## 9. Security and SSDLC check

Only synthetic runtime/class-header data is tested; no broker, database, credentials or network service is used. JUnit/plugins are exact managed/pinned release artifacts. Report generation is not an authorization, redaction or SAST control.

## 10. Lessons learned and knowledge checks

1. Discovery counts matter.
2. Failsafe verifies after integration execution.
3. Expected failure must produce a failing build, not only a log.
4. Tooling integration is distinct from business integration.
Knowledge check: does mvn integration-test alone prove the final gate passed? Use verify. Unknown: hosted CI behavior in later tasks.
