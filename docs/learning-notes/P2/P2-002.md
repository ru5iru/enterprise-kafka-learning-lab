## 1. Goal and context

Understand why a dependency can compile tests without being needed by production code. Review all Maven scopes before future Spring/Kafka/JDBC dependencies are introduced; do not add them now.

## 2. Concepts explained in my own words

Scope selects classpaths and affects propagation to consumers. It does not choose a version or make a dependency safe.

| Scope | Compile / runtime / test use | Consequence |
|---|---|---|
| compile (default) | available throughout | Usually propagates to consumers |
| provided | compile and tests, runtime supplied externally | Not propagated; runtime absence can fail |
| runtime | runtime and tests, not main compilation | Suitable for implementations loaded through another API, when intentionally configured |
| test | tests only | JUnit must not become a production requirement |
| system | provided-like, explicit local file | Nonportable; avoid |
| import | POM in dependencyManagement | Imports managed entries, adds no executable JAR |

The existing Boot BOM manages versions; only an explicit dependency introduces a library. optional restricts downstream automatic inclusion; exclusions remove specific edges and need compatibility review. Transitive mediation and dependency convergence deserve inspection, not speculative scope changes. Plugin dependencies are separate from the application dependency graph.

## 3. Work performed and artifact

Reviewed root management and child JUnit scope. WSL dependency-plugin 3.11.0 generated three temporary classpaths; javac rejected a JUnit import without test dependencies and accepted it with them. No production source/module or POM changed.

## 4. Decisions and rationale

Keep JUnit test scope and BOM-owned version. Promoting it to compile just to fix an IDE classpath would hide wrong source roots; fix the root instead. Avoid system paths and unreviewed exclusions. Existing dependency ADR applies, no new architecture choice.

## 5. Best practices and design patterns

Use minimal dependency exposure, explicit intent and build inspection. Scope is build separation, not dependency inversion or a service-security boundary. Future Boot packaging may handle libraries differently and must be verified at its task.

## 6. Common mistakes, errors and vulnerabilities

Compile success can hide runtime missing classes when provided is misused; test scope can hide accidental main-source imports. Negative JUnit compilation verified the latter boundary. Vulnerable transitive libraries remain possible regardless of scope; SCA is deferred to P2-032 and later release work.

## 7. Testing, verification and evidence

Executed WSL three-scope classpath resolution with pinned dependency goal. Observed empty compile/runtime dependencies and managed JUnit 6.1.3 on test classpath; import rejected/accepted as expected. Exact driver and output in evidence. Other scope cases reviewed against documentation; not claimed as executed runtime experiments.

## 8. Debugging and operational notes

For ClassNotFoundException compare runtime classpath and packaging; for compile errors compare source root and scope. dependency:build-classpath includeScope is a threshold (compile includes provided/system, runtime includes compile), not an exact POM-scope equality filter. Keep diagnostics in Linux cache/temp paths, not committed classpath files.

## 9. Security and SSDLC check

No remote credential or local system JAR path added. HTTPS Central/strict checksums remain existing policy. Narrow test scope reduces production dependency surface but is not SCA, attestation or runtime isolation. No new network listener.

## 10. Lessons learned and knowledge checks

Learned: BOM import adds no JAR; scope and version are independent; classpath filters use thresholds; plugin and application graphs differ. Can explain why JUnit import fails on production classpath and why provided is a deployment assumption. Next review abstraction contracts.
