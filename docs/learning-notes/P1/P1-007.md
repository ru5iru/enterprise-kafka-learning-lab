## 1. Goal and context

Review rules connect a proposed change to evidence and an intentional merge. P1-006 is Done and published. This task defines review responsibilities/outcomes; it does not configure GitHub protection or start CI.

## 2. Concepts explained in my own words

An approval is a reviewer judgment about a particular diff, while a successful check is observed verification at a commit. User authorization permits a Git action but does not prove acceptance. Self-review is useful in a single-owner lab when labeled honestly; it does not become independent review by being written in a PR body.

## 3. Work performed and artifact

Added author/reviewer duties, required evidence, disclosed self-review, six outcome scenarios, final-head recheck, merge/hash trade-offs and recovery. Linked Definition of Done and the PR template. Reused known absence of protection/CI instead of claiming enforcement.

## 4. Decisions and rationale

Allow explicit self-review for scoped learning work so the policy fits one learner. Alternative: require an unavailable second approver for every documentation edit; rejected because it would fabricate or block ordinary review without improving evidence. Retain human decisions for unresolved requirement conflicts and user Git authorization. No architecture/security technology decision is introduced, so no new ADR is needed.

## 5. Best practices and design patterns

Review the actual diff and its base, separate blockers from suggestions, and recheck affected evidence after material changes. Preserve published hashes where task evidence depends on them. The relevant pattern is a review gate with traceability; Kafka delivery patterns are not implemented. Server enforcement remains absent.

## 6. Common mistakes, errors and vulnerabilities

Potential errors include calling absent CI green, treating a clean diff as functional proof, approving a stale head, silently clearing incomplete dependencies and publishing sensitive logs. The documented decision table covers each. It was self-reviewed against project rules; no GitHub denial or incident was manufactured.

## 7. Testing, verification and evidence

Ran static coverage checks over responsibilities/outcomes, checked actual P1-006 CSV/evidence/note traceability and verified no workflow YAML exists. The six scenarios were reviewed as documentary accept/block/recheck cases. Runtime tests and a real PR approval were not applicable to defining this policy.

## 8. Debugging and operational notes

When a check fails, keep its observation, fix the cause and rerun affected checks. When a base/head changes, review the resulting diff before merge. Use a traceable revert and dependency review for regressions; do not erase historical evidence or force-reset main.

## 9. Security and SSDLC check

The asset is trusted review/merge evidence at the workstation-to-GitHub boundary. Sensitive findings use private reporting and exposed credentials need revocation/rotation. This policy does not turn on protection or scanning. Technical review details expand at P1-036 and automated checks begin at P1-037.

## 10. Lessons learned and knowledge checks

1. Authorization, review and test results are distinct facts.
2. No configured CI is not a passing CI run.
3. A new head can invalidate an earlier review.
4. Honest self-review is more useful than invented independent approval.
Knowledge check: what happens when an applicable verification fails? Fix and recheck before merge. Unknown: future enforcement settings.
