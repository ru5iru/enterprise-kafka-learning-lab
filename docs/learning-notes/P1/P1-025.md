## 1. Goal and context

P1-025 installs native Kafka CLI tools inside WSL after P1-024. It enables future broker experiments without prematurely starting/configuring infrastructure.

## 2. Concepts explained in my own words

Kafka client/admin programs run on a JVM and talk to brokers only when an operation/address is supplied. A local --version establishes classpath/runtime startup, not cluster connectivity. Producer, consumer, broker and KRaft controller are different responsibilities even when one distribution ships scripts for all of them.

## 3. Work performed and artifact

Installed hash-pinned Kafka 4.4.0 Scala 2.13 distribution, selected its bin/KAFKA_HOME through the launcher, and added CLI usage/boundary guidance. Verified topic-admin and console-consumer startup plus invalid-option rejection. No server script or network operation ran.

## 4. Decisions and rationale

Use current official binary distribution with a recorded pin rather than an arbitrary preinstalled Windows script or mutable image CLI. Use verified transport fallback for Apache downloads without weakening TLS/hash checks. The CLI pin does not silently select the future broker image; ADR-0003 still governs KRaft architecture.

## 5. Best practices and design patterns

Keep tool installation separate from resource creation, record exact artifact identity and validate expected argument errors. Avoid auto-topic/server startup during setup. Client/server separation is the relevant architectural concept; publish/subscribe is planned, not implemented.

## 6. Common mistakes, errors and vulnerabilities

CLI availability can be mistaken for a running cluster, server scripts can accidentally start infrastructure, and a changing binary can undermine repeatability. Versioned/hash-pinned installation and version/parser-only checks avoid those errors. Broker protocol/security behavior remains explicitly unknown.

## 7. Testing, verification and evidence

Actual publisher archive/hash acquisition and Linux extraction were executed. Evidence checks two CLI entry points on Java 25 and exact invalid-option diagnostics. No topic/message/broker test is invented or marked complete.

## 8. Debugging and operational notes

Check the project environment, Java version and KAFKA_HOME for startup issues. Diagnose parser errors before connectivity. For download trust failure, use reviewed verified transport; do not use insecure flags. Rollback only the versioned tool install after checking users.

## 9. Security and SSDLC check

The boundary is publisher JVM binaries into Linux tooling. TLS/hash/version pin, explicit privilege during install and no remote broker address apply. The full distribution ships server capabilities, but none is activated. No credentials, real payloads or network service were added.

## 10. Lessons learned and knowledge checks

1. CLI installation is not cluster deployment.
2. Admin and consumer programs are clients.
3. A CLI version pin is separate from future broker-image compatibility.
Knowledge check: can this prove delivery semantics? No records were sent. Unknown: first broker/network/message behavior in P3.
