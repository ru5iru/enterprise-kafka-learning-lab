## 1. Goal and context

P1-028 makes type responsibilities understandable before Java source appears. P1-027 is Done/pushed. This documents names, not a new class hierarchy or business abstraction.

## 2. Concepts explained in my own words

Type names communicate roles, while Java syntax/visibility and package ownership determine actual language boundaries. Events describe recorded facts and commands express intent. A name is a review aid, not proof of behavior, retry semantics or security.

## 3. Work performed and artifact

Added examples for values, events, requests, adapters, controllers, exceptions and unit/integration tests, plus rejected catch-all/prefix/environment cases. Included exact-case filenames and future rename/discovery implications. No classes were generated.

## 4. Decisions and rationale

Use concrete semantic role names instead of I prefixes and automatic Impl/Manager/Utils buckets. Keep existing OrderCreated event terminology. Interfaces/records are introduced only for actual boundary/immutability needs after compatibility review, avoiding speculative design.

## 5. Best practices and design patterns

Prefer single responsibilities, recognizable roles, past-tense facts and case-portable filenames. Preserve public/generated contracts during renames. Naming supports encapsulation and review; it does not implement dependency inversion or immutable event semantics.

## 6. Common mistakes, errors and vulnerabilities

A Windows tree can hide filename-case errors that fail in Linux CI. Conflating CreateOrderRequest with OrderCreated obscures intent versus fact; catch-all names hide coupling. Negative documentary examples cover these cases, while actual compile/serializer/discovery checks remain future work.

## 7. Testing, verification and evidence

Static/self-review checked role coverage, counterexamples, package alignment and absent application structure. No runtime, compilation, test discovery or serialization behavior was claimed. Evidence points to the reviewed convention and exact checks.

## 8. Debugging and operational notes

For a later naming failure, inspect declaration/file case, imports and test patterns. Public/reflected/generated names need consumer-aware migration. Correct documentation with a normal commit rather than generating placeholder types.

## 9. Security and SSDLC check

Names must not encode credentials/customer/environment data. A misleading exception name must not become an automatic retry rule. Actual authorization and event validation remain implementation controls, not naming guarantees.

## 10. Lessons learned and knowledge checks

1. Intent and facts deserve distinct names.
2. Linux filename case matters even when local edits look fine.
3. Interfaces and records must earn their role.
Knowledge check: does Retryable in a class name prove replay safety? No. Unknown: actual serializer/test discovery behavior later.

## 11. Completion decision and handoff

Acceptance is met by tailored naming rules/examples and review evidence. Only P1-028 is Done. Publish before P1-029 defines error handling.
