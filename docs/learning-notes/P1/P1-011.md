## 1. Goal and context

CONTRIBUTING.md turns repository rules into an actionable contributor journey. P1-010 is Done and pushed. This task is scoped onboarding documentation, not new automation, runtime code or a second competing governance policy.

## 2. Concepts explained in my own words

A useful contribution joins the task specification, smallest deliverable, evidence and review in one traceable change. A local staged diff is the proposed commit content; the working diff alone can miss already staged files. CSV tracking reflects acceptance rather than the existence of a commit or closed issue.

## 4. Decisions and rationale

## 5. Best practices and design patterns

Use task-sized changes, preserve existing user edits, stage explicit paths and review both working and cached whitespace. Tie Done to evidence and disclose unsupported tests. This is a traceability workflow; no application pattern is implemented. Future CI enforcement and Java standards remain their own tasks.

## 6. Common mistakes, errors and vulnerabilities

Risk examples include running placeholder commands literally, git add-all accidentally staging credentials, resaving CSV through a lossy spreadsheet, claiming no-CI as success and interpreting issue closure as task completion. Wording and static review address these errors. Actual contributor behavior and tool integrations remain untested.

## 8. Debugging and operational notes

For a rejected contribution, identify the exact missing acceptance/evidence item instead of regenerating unrelated files. Inspect staged versus working changes before correcting. If a document step is wrong, use a new correction; never erase a real failed observation or reset shared history.
