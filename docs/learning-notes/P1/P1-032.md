## 1. Goal and context

P1-032 defines reproducible dependency/build management before plugin implementation. P1-031 is Done/published. It must enable real P1 tool/CI evidence without creating the later Spring application.

## 2. Concepts explained in my own words

A BOM manages library versions but does not declare dependencies. Maven plugin management is separate from execution and from installed Maven/JDK versions. Plugin classloaders may use dependencies outside the project BOM. A reactor can aggregate checks without forcing service runtime coupling.

## 3. Work performed and artifact

Added dependency policy and ADR-0013, reviewed actual Boot requirements/BOM and publisher metadata, and recorded exact stable pins plus the tooling-only verification-module design. No POM or source module is created yet.

## 4. Decisions and rationale

Use Boot management for its library family and explicit pins for invoked plugins. Reject hand-mixed framework/client versions, mutable remote snapshots and an empty build masquerading as tested code. A small tool probe resolves P1 CI prerequisites while preserving P2/P3 scope and independent services.

## 5. Best practices and design patterns

Declare narrow scopes, inspect effective models/trees, review exclusions/overrides and use verified HTTPS/checksums. Keep source revision snapshots distinct from unpinned remote inputs. Reproducible builds and independent-module ownership are the patterns; no business library is shared.

## 6. Common mistakes, errors and vulnerabilities

Common errors are assuming a BOM adds code, pluginManagement runs a goal, a warm cache proves fresh resolution or a zero-test build proves testing. Reviewed rejection scenarios cover these. Source metadata cannot prove the whole selected matrix or absence of vulnerabilities.

## 7. Testing, verification and evidence

Actual primary-source reads confirmed current Boot/JUnit and stable plugin versions. Static/documentary review checked management/activation/scope distinctions and absence of premature build/app files. Joint resolution/execution, scans and hosted CI remain not run.

## 8. Debugging and operational notes

For later resolution failure, distinguish unavailable artifact, incompatible plugin prerequisite, checksum/trust and settings. Review a pin change with actual regression evidence instead of bypassing verification. Preserve caches unless targeted diagnosis justifies action.

## 9. Security and SSDLC check

The supply-chain boundary is remote artifacts/plugin code into local builds. HTTPS, explicit pins/scopes, no embedded credentials and reviewed exceptions are requirements. A resolved BOM is not SCA/SBOM/security certification; no new repository trust root was added.

## 10. Lessons learned and knowledge checks

1. Management and activation differ.
2. Plugins and project libraries have different dependency realms.
3. Real tool tests can exist without a business application.
4. A source-reviewed pin still needs executed compatibility checks.
Knowledge check: does importing Boot BOM run a Spring app? No. Unknown: actual plugin/CI results in following tasks.
