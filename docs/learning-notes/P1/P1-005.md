## 1. Goal and context

Branch names should connect a review to one stable roadmap task. P1-004 is Done and published. The change formalizes repository collaboration, not Kafka topology or runtime release branching.

## 2. Concepts explained in my own words

A branch is a movable reference to a commit. A descriptive name helps humans find scope, while commit ancestry determines included changes. Git accepts more names than this repository wants; a syntactically valid name can still use an unknown task or misleading suffix.

## 3. Work performed and artifact

Expanded contribution workflow with allowed types, exact task-ID case, lowercase kebab suffixes, seven review examples, CLI syntax guidance, stacked-base exception and safe naming-error recovery. Historical P0 refs are left intact.

## 4. Decisions and rationale

Keep the established type/task/description format because it joins branch, commit, CSV and evidence. Alternative: branch per service or GitFlow develop/releases; rejected because learning tasks span services and no release process exists yet. Document authorized stacking to avoid either unpublished dependency work or an unrequested merge. No new architecture decision is made.

## 5. Best practices and design patterns

Traceability and focused change review are the relevant practices. Check task membership, not just a regex-shaped number. Distinguish a PR base from main when reviewing a stacked task. No application pattern is involved; server-side enforcement is explicitly deferred.

## 6. Common mistakes, errors and vulnerabilities

A branch such as docs/P1-999-branch-naming is Git-valid but refers to no task. Case/underscore/type aliases can fragment lookup conventions. Embedding user data or tokens in names exposes them in refs and logs. The examples and rejection checks address naming mistakes; content secrecy still requires review.

## 7. Testing, verification and evidence

Checked three documented good names against the grammar, CSV and Git, four policy-invalid names against grammar/membership, and three malformed refs against Git. All observed outcomes match. No branch was created for a negative probe and no deployed validator is claimed.

## 8. Debugging and operational notes

If Git rejects a name, run check-ref-format without modifying refs. If Git accepts it but policy rejects it, verify type, case, slug and task existence. Correct an unpublished name non-destructively; coordinate published corrections and preserve recovery references.

## 9. Security and SSDLC check

Branch refs are public metadata in this repo. Naming rules forbid secrets/customer identifiers, and no settings or credentials were changed. GitHub protection remains absent as observed in P1-001. Manual review is policy, not proof of enforced protection.

## 10. Lessons learned and knowledge checks

1. Names communicate scope; ancestry defines actual content.
2. A regex-shaped task ID may not exist.
3. Stacked work needs a stated review base.
4. Ref syntax and local policy are separate checks.
Knowledge check: why does a task branch based on its predecessor include earlier work? Unknown: future ruleset enforcement.
