## 1. Goal and context

P1-029 defines how future failures remain observable and safe after type naming. P1-028 is Done/pushed. No runtime handlers or retry topology are created.

## 2. Concepts explained in my own words

An exception carries causal information; a handling boundary decides recovery, rejection or termination. Asynchronous enqueue and eventual acknowledgement are different moments. A consumer side effect and its offset commit are different operations, so replay/timeout outcomes can be ambiguous.

## 3. Work performed and artifact

Added an eight-category policy table with cause preservation, interrupt/cancellation handling, bounded retry ownership, producer callback/future observation, explicit consumer-offset decisions, cleanup and safe translation. Reviewed concrete documentary scenarios against existing SSDLC rules.

## 4. Decisions and rationale

Classify by actual recovery semantics rather than retrying every exception or wrapping every failure into RuntimeException. Preserve cancellation and unknown outcomes. Alternative silent catch/default success hides learning/data-loss evidence and is rejected. This formalizes existing guardrails without a new architecture ADR.

## 5. Best practices and design patterns

Fail fast for deterministic invalid configuration, centralize translation/logging at meaningful boundaries, preserve cause/primary errors and require idempotency analysis for replay. Boundary handling and bounded recovery are relevant patterns, not implemented retry/DLT behavior.

## 6. Common mistakes, errors and vulnerabilities

Swallowed failures, log-and-rethrow duplication, retry storms, erased interrupts, enqueue-as-success and implicit offset advance can lose or duplicate work. Documentary walkthroughs identify these failure modes; none is falsely reported as an executed broker experiment.

## 7. Testing, verification and evidence

Executed static policy coverage and self-reviewed eight categories/representative cases. Official producer async semantics and Java interruption references were reviewed. Runtime negative tests are not applicable to defining the standard and remain deferred explicitly.

## 8. Debugging and operational notes

For future incidents, identify synchronous versus asynchronous failure and side-effect/offset state before replay. Keep safe error codes and causal diagnostics. Correct policy/contracts with consumer review rather than weakening error paths to hide an issue.

## 9. Security and SSDLC check

Exception messages may contain credentials/payloads; preserving cause in memory does not authorize leaking it through APIs/logs. Authentication denial is not a reason for blind retry. Runtime authorization, DLT and secure diagnostics still need actual implementation/tests.

## 10. Lessons learned and knowledge checks

1. Failure classification controls recovery.
2. Timeouts can have unknown publication outcomes.
3. Interrupts represent cancellation, not retry invitations.
4. Offset progress is not automatically business success.
Knowledge check: does Kafka producer idempotence guarantee external side effects exactly once? No. Unknown: observed failure behavior in P3/P6.

## 11. Completion decision and handoff

Acceptance is met by tailored standards, alternatives/security review and honest documentary evidence. Only P1-029 is Done. Publish before P1-030 defines logging conventions.
