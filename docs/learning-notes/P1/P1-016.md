## 1. Goal and context

Install the owner-selected Maven baseline in WSL after P1-015 compiler verification. This task establishes a Linux Maven executable, not a service build or plugin configuration.

## 2. Concepts explained in my own words

Maven is a Java process with its own distribution and dependency/plugin resolution. Maven home and Java home should both be Linux paths. A binary checksum checks downloaded bytes; it does not establish whether future dependency repositories are reachable or every plugin supports the JDK.

## 3. Work performed and artifact

Added a pinned Maven installer with optional verified local archive input, selected its Linux bin path in the project environment, and documented the transport fallback. Installed 3.10.2 under /opt/kafka-lab and observed its version/JDK/OS. Invalid argument count is rejected.

## 4. Decisions and rationale

Use the previously reviewed 3.10.2 distribution rather than Ubuntu default or inherited Windows 3.9.9. WSL could not validate Apache TLS, so use Windows verified transport and Linux SHA-512 enforcement instead of disabling verification. Alternative: import an unreviewed CA globally; rejected. No baseline version change or new ADR is needed.

## 5. Best practices and design patterns

Pin acquisition bytes, isolate versioned installation, keep tool selection explicit and record failed transport honestly. Avoid automatic replacement of unrelated tools. Reproducible acquisition is the pattern; Maven lifecycle/build configuration remains later work.

## 6. Common mistakes, errors and vulnerabilities

The actual failure was TLS trust-chain validation, not a missing archive/version. The fallback preserves certificate/hash checks. A working --version can still hide later resolution failures, which P1-017 will test. Excess arguments fail with usage 64; no archive overwrite path is offered.

## 7. Testing, verification and evidence

Executed verified download, SHA-512-checked extraction, Linux Maven version/JDK/OS checks and invalid-argument rejection. Evidence preserves observed output. No dependency resolution or Maven build is claimed in this installation task.

## 8. Debugging and operational notes

If mvn resolves to /mnt/c, use the project launcher. For TLS failures, distinguish trust from artifact existence and never use -k to mask it. Rollback affects only the new versioned directory and project PATH, after consumer review.

## 9. Security and SSDLC check

Boundary: Apache distribution download to a privileged Linux directory. TLS transport plus pinned SHA-512, root gate and bounded arguments apply. No credentials, custom trust root or global Windows setting changed. A separate signature audit remains unperformed.

## 10. Lessons learned and knowledge checks

1. Download host and install/runtime host can differ without mixing executables.
2. A TLS failure is not a reason to skip verification.
3. Maven banner success is weaker than dependency resolution.
Knowledge check: which Maven does the launcher run? The versioned Linux 3.10.2. Unknown: repository resolution until P1-017.

## 11. Completion decision and handoff

Installation acceptance is met with actual Linux selection and recovery evidence. Only P1-016 is Done. Publish this task before P1-017 verifies lifecycle and failure behavior.
