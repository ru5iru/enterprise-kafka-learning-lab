## 1. Goal and context

## 2. Concepts explained in my own words

The JVM specification separates per-thread execution state/frames from shared heap and method-related structures without prescribing a physical object layout or collector. HotSpot adds concrete implementation categories such as metaspace and code cache. A local reference can be in a frame while its target object is on the heap; optimized allocation is an implementation detail, not a reason to design around guessed addresses.

GC reclaims unreachable managed objects, not every object no longer useful to the business. Static maps, queues, callbacks, thread-locals and long-lived caches can keep unwanted data reachable. Collector timing is not a resource-release contract. Close files/connections explicitly; direct/native buffers, thread stacks, metadata and other native allocations mean -Xmx is not total process memory.

Observe trends in used/committed/max heap and nonheap plus process/container metrics. NMT is a HotSpot diagnostic with coverage limits, disabled by default and enabled at startup; it is not a complete native/RSS accounting tool. Do not infer a universal heap ratio, GC algorithm or pause budget from this review.

## 4. Decisions and rationale

Use tiny isolated capped subprocesses instead of exhausting a shared JVM or testing host/container OOM. Disable heap dumps explicitly because memory images can contain sensitive data. Keep observations qualitative except reported actual cap. No new memory-tuning ADR because no application sizing decision was made.

## 5. Best practices and design patterns

Applies explicit resource lifecycle and bounded-retention reasoning. Reachability is a graph of references, not equivalent to usefulness or variable scope. Caches/buffers/queues need application-specific budgets later; this review implements none.

## 6. Common mistakes, errors and vulnerabilities

Observed invalid heap configuration and isolated heap exhaustion with nonzero exit. Reviewed memory leaks through reachable references, too many platform-thread stacks, native/direct growth and insecure dump publication. No OS OOM or production leak diagnosed. Catching OutOfMemoryError and continuing normal work is not a recovery policy here.

## 8. Debugging and operational notes

If RSS exceeds heap, inspect nonheap/native/thread/direct categories and container accounting before simply increasing Xmx. If heap grows after collections, inspect reference owners/retention and safe diagnostics. Do not call System.gc and assert prompt reclamation. Heap dumps require explicit private handling and are not committed.

## 9. Security and SSDLC check

Availability and confidentiality both matter: unbounded retained input can exhaust memory, while diagnostic dumps can expose tokens/data. The experiment has synthetic bytes, process caps/timeouts and no dumps/listeners. NMT/heap views do not establish a complete security/resource boundary. Root-default WSL remains inherited.

## 10. Lessons learned and knowledge checks

Learned: heap differs from process memory; reachability differs from usefulness; GC is not close(); flags can fail before main; OOM should remain visible. Can explain why bounded worker count still permits queue retention and why Xmx is not a container budget. Next SLF4J logging facade/provider behavior.
