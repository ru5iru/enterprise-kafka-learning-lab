## 1. Goal and context

P1-015 verifies the selected Linux compiler actually works rather than relying on a version banner. P1-014 is Done/pushed. Maven/Spring/application implementation remain outside this experiment.

## 2. Concepts explained in my own words

javac turns source into bytecode; --release constrains the target language/API/class format. java executes the resulting class. A successful version command proves neither compilation nor useful execution, so the probe verifies the entire small chain and checks failure behavior.

## 3. Work performed and artifact

Added verify-java.sh and its usage/limits document. Ran it twice in WSL: compile/run at release 25 succeeded with expected output and major 69; malformed source and release 99 returned failure. Temporary source/classes/logs are cleaned by a scoped trap.

## 4. Decisions and rationale

Use temporary synthetic code instead of a permanent starter application, preserving the P2 boundary. Alternative: only javac --version; rejected because it cannot establish compilation/runtime compatibility. Explicit release avoids accidental reliance on the installed default target.

## 5. Best practices and design patterns

Positive and adversarial compiler checks, deterministic expected output, isolated temporary state and exit-status propagation apply. This is an executable toolchain probe, not a service/application pattern. Maven, plugins and automated CI remain later tasks.

## 6. Common mistakes, errors and vulnerabilities

A PATH mismatch could pair different compiler/runtime versions, malformed source must not yield valid bytecode, and unsupported targets must fail. The script observed these checks rather than assuming them. It does not prove all Java APIs or future dependency compatibility.

## 7. Testing, verification and evidence

Two real WSL runs passed all assertions; the evidence preserves commands and sanitized output. The negative source leaves no Broken.class and release 99 is rejected. No unit test framework, Maven build or broker was used.

## 8. Debugging and operational notes

Identify which of version, compile, run, class inspection or negative assertions failed. Confirm the project environment first. Do not weaken release/error checks to hide a mismatch. Unique temp files are removed on normal/error exit; no global rollback is required.

## 9. Security and SSDLC check

Only fake source is compiled, under Linux /tmp. No network service, credential, downloaded dependency or untrusted payload executes. The checked-in script resolves the reviewed project JDK and removes only its own named temporary files.

## 10. Lessons learned and knowledge checks

1. A banner is weaker than compile plus execution.
2. --release makes target expectations explicit.
3. Expected failures are observable successful verification cases.
Knowledge check: does this prove Spring compatibility? No. Unknown: Maven/plugin behavior until its verification tasks.

## 11. Completion decision and handoff

Acceptance is satisfied by the repeated experiment and observed versus expected positive/negative behavior. Only P1-015 becomes Done with evidence. Publish before P1-016 installs Linux Maven.
