## 1. Goal and context

Learn how clients depend on a capability without knowing its implementation. This supports future adapter testing, but this task does not introduce a service, Kafka publisher port or Spring dependency injection.

## 2. Concepts explained in my own words

An interface names a supported operation and allows unrelated classes to implement it. An abstract class can additionally hold instance state and shared construction/implementation, but consumes the single class-inheritance relationship. Interface default methods supply behavior, not automatic per-object state; constants can still reference mutable objects and should not be treated as a safe global store.

A useful abstraction defines preconditions, results, failure, blocking and resource-ownership rules. A matching signature alone does not prove substitutability. The temporary SizePolicy contract accepts a nonnegative size and returns a bounded accepted size. Exact and Capped satisfy this contract while choosing different strategies. Prefer composition when shared inheritance is merely code reuse; avoid an interface for every concrete class without a real boundary.

## 3. Work performed and artifact

Created the canonical review and executed an isolated Java 25 compiler/runtime probe. It substitutes two SizePolicy implementations through the same client, checks shared rejection behavior and attempts an incomplete Runnable implementation. Source is embedded in the evidence driver; no reusable business API was created.

## 4. Decisions and rationale

Choose a tiny local strategy contract over a speculative EventPublisher interface whose Kafka ack/timeout semantics are not yet learned. Prefer an interface for independent capabilities; use an abstract class only for a genuine shared invariant/state relationship. No architecture decision changes or new ADR.

## 5. Best practices and design patterns

Strategy and programming to an interface apply to the synthetic example. Contract consistency and narrow responsibility matter more than suffixes or implementation counts. Adapter/ports patterns are conceptual future options, not installed service layers.

## 6. Common mistakes, errors and vulnerabilities

A fake implementation can satisfy syntax yet accept invalid inputs or hide failures; both examples explicitly reject negatives. Missing method compiler rejection was executed. A generic send() that hides whether completion means enqueue or broker acknowledgement is a future API risk, not a verified Kafka behavior here.

## 7. Testing, verification and evidence

Compiled with release 25, all lint and warnings-as-errors; ran with assertions enabled in WSL. Two strategies returned 10/4 and rejected negative sizes. javac rejected the incomplete Runnable class. Exact bounded driver and actual output are in evidence; no framework test claimed.

## 8. Debugging and operational notes

When a class cannot implement an interface, inspect method visibility/signature/return/throws compatibility. When it compiles but tests fail, review the behavioral contract, not just types. Do not use casts or catch-all defaults to hide a contract mismatch.

## 9. Security and SSDLC check

No secrets, dependencies, network or persistent source added. An abstraction is not a security control; implementations must still validate inputs, preserve failure signals and define resource ownership. No authorization or TLS guarantees inferred from an interface.

## 10. Lessons learned and knowledge checks

Learned: interface and abstract class solve different needs; signatures omit many behavioral promises; composition avoids accidental inheritance coupling; a fake must honor the same failures. Can explain when an interface is worth adding and why enqueue/ack ambiguity is dangerous. Next dependency inversion.
