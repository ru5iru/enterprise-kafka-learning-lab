## 1. Goal and context

P1-017 tests real Maven behavior after P1-016 installation. A version banner is insufficient, and the prior Apache TLS failure makes endpoint-specific evidence important. No application/service implementation is included.

## 2. Concepts explained in my own words

Maven builds an effective project model and resolves plugins/transitive artifacts from repositories into a local cache. A fresh cache tests network resolution; an offline repeat tests local reuse. A packaging=pom temporary project exercises model/plugin behavior without adding premature Java services.

## 3. Work performed and artifact

Added an isolated verification script and guidance. The first run and final repeat each used fresh temporary repositories, generated an effective POM with Help Plugin 3.6.0, succeeded offline afterward, and rejected malformed XML/unknown phase. Cleanup removed only the probe tree.

## 4. Decisions and rationale

Pin the verification plugin explicitly using observed Central metadata instead of relying on prefix/LATEST resolution. Alternative: use an existing warm ~/.m2 cache; rejected because it could hide broken repository access. This probe pin does not decide future application dependency management; no new ADR is needed.

## 5. Best practices and design patterns

Compare cold and cached behavior, check strict artifact checksums, isolate synthetic files and propagate nonzero exit status. Do not treat expected rejection as a test failure. The relevant pattern is reproducible environment verification; no Kafka semantics are implemented.

## 6. Common mistakes, errors and vulnerabilities

A warm cache could mask network failure, an unpinned plugin could change between runs, and swallowed Maven errors could create false completion. These are controlled by isolated repositories, an explicit pin and checked status. The actual negatives are malformed POM and invalid lifecycle phase; they were observed rejected.

## 7. Testing, verification and evidence

Both complete experiments passed their online/offline and failure assertions. The evidence includes the final execution command/output and links the exact script. No compiler plugin, Spring service or CI run is claimed by this task.

## 8. Debugging and operational notes

If online fails but offline passes, inspect access/cache separately. If model parsing fails, correct XML rather than calling install again. If checksums or TLS fail, fix acquisition/trust through reviewed configuration; never bypass verification. Prefix-checked temporary cleanup is the only teardown.

## 9. Security and SSDLC check

Network boundary: verified Maven Central into an isolated cache. No credentials, private repositories, custom trust roots or real payloads were used. Maven plugins execute code, so the pin and publisher source matter; this is not a vulnerability scan or complete supply-chain assurance.

## 10. Lessons learned and knowledge checks

1. Cold and offline checks answer different questions.
2. One TLS endpoint failure does not prove another endpoint fails.
3. A valid Maven installation can still reject a bad project/phase correctly.
Knowledge check: why isolate the local repository? To expose true resolution behavior. Unknown: full project compatibility until later configuration.

## 11. Completion decision and handoff

Acceptance is met by two observed repeatable experiments and negative outcomes. Only P1-017 is Done with evidence. Publish before P1-018 installs the Linux container engine.
