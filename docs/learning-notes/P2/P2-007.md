## 1. Goal and context

Review stable value carriers and how to prevent callers from changing captured data. Future event payloads need predictable state, but actual Kafka event/schema design belongs to its own tasks.

## 2. Concepts explained in my own words

A record declares components, final component fields, accessors and generated value-oriented methods; it can validate/normalize in a canonical or compact constructor. Final references do not freeze their referents. A record holding a mutable list can visibly change without assigning its field.

The probe contrasts Shallow with Snapshot: copying a List<String> into an unmodifiable list prevents input-container and accessor mutation. Mutable elements need additional copying/immutable models. Arrays require copying on ingress and egress; default array component equality is array identity, not content comparison. Generated toString can expose every component: do not log records holding secrets or payloads.

Use a class when mutable lifecycle/identity or encapsulated representation is essential. A Java record declaration does not define a compatible JSON/Avro schema or an idempotency key. Value equality is useful locally and must not be confused with distributed event identity.

## 3. Work performed and artifact

Executed isolated records with a mutable input list, a defensive copy and compact constructor invariant. Checked equality/hash consistency, rejected empty/null construction, unmodifiable accessor mutation and direct final-component assignment. Added no service DTO/event class.

## 4. Decisions and rationale

Choose copy plus immutable elements for this finite demonstration; merely final fields or unmodifiable wrappers would retain aliases. Do not create a production record hierarchy or add Lombok to reduce code. Existing immutable-model policy applies; no new architecture/ADR.

## 5. Best practices and design patterns

Applies value objects, constructor invariants and defensive copying. Record syntax reduces mechanical code but leaves input bounds and secrecy policy to the author. Serializer integration, wire evolution and event identity remain deferred.

## 6. Common mistakes, errors and vulnerabilities

Observed shallow alias mutation; snapshot stayed unchanged. Observed rejected constructor/accessor mutation and compiler rejection of final reassignment. Hypothetical remaining risks include mutable elements, array equality, sensitive toString and oversized retained payloads. No production serialization or security test claimed.

## 7. Testing, verification and evidence

WSL release25/all-lint/Werror and assertions passed. Input list mutation changed shallow size2 while snapshot stayed size1; equal snapshots had equal hash codes. Empty/null/accessor mutation rejected; Broken record assignment failed compilation. Exact source/output retained in evidence.

## 8. Debugging and operational notes

If an immutable value changes, trace every reachable mutable component and exposed accessor. Use a compact-constructor parameter reassignment to store a validated copy; do not assume a record automatically deep-copies. Never parse generated toString as a protocol. No runtime rollback required.

## 9. Security and SSDLC check

No secrets or personal data in synthetic components. Generated representation can leak data, and unbounded inputs still exhaust memory even when immutable. Future ingestion requires validation/redaction/retention controls; not supplied by the record keyword.

## 10. Lessons learned and knowledge checks

Learned: records are shallow carriers; final differs from deep immutability; constructor/accessor boundaries both matter; local equality differs from event identity. Can explain why List<String> copying works here but List<MutablePayload> needs more care. Next checked/unchecked failure contracts.
