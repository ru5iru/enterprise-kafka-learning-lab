## 1. Goal and context

P1-022 connects the existing editor/current workspace to verified WSL tools after P1-021. The owner asked to keep development here while executing in Linux, so no second checkout or Windows toolchain is introduced.

## 2. Concepts explained in my own words

An editor frontend can run a process elsewhere. A VS Code process task passes an argument vector directly; a shell task adds another parsing layer. Workspace configuration can be versioned without sharing personal user settings. The task runner is distinct from Java language-server/debugger setup.

## 3. Work performed and artifact

Added a root workspace file with Ubuntu terminal profile and two Java/Maven process tasks, plus usage/limits documentation. Verified existing VS Code CLI and executed the resolved task vectors in WSL. Linux defaults also allow an optional remote session; no UI launch was claimed.

## 4. Decisions and rationale

Adopt the installed VS Code instead of installing another editor. Use a tracked workspace file because .vscode is intentionally personal/ignored. Alternative: Windows Java settings pointing at Linux binaries; rejected because those executables cannot serve a Windows-hosted JVM directly. No new architecture ADR beyond the existing WSL decision is needed.

## 5. Best practices and design patterns

Keep host and runtime roles explicit, quote through separate args, avoid automatic run-on-open commands and leave personal settings untouched. This is a host/runtime adapter pattern for tooling, not a business service pattern. Formatter/inspections follow separately.

## 6. Common mistakes, errors and vulnerabilities

Common errors are running Windows mvn through inherited PATH, executing interpolated shell strings, or assuming a terminal profile selects JAVA_HOME. The task vectors invoke the project launcher directly and tested Linux versions. GUI/index/debug behavior remains explicitly unverified.

## 7. Testing, verification and evidence

Existing code CLI returned 1.107.1/x64. JSON shape checks and actual WSL task-vector execution passed for Java/Maven. No editor window, Java language server, remote extension or application debugging test ran; the evidence distinguishes those limits.

## 8. Debugging and operational notes

For task failure, inspect configured command/argument paths and the WSL launcher before editing global settings. Use the optional workspace or continue the current editing app. Close/revert the workspace to roll back; no shared source move or user preference reset is necessary.

## 9. Security and SSDLC check

The boundary is editor-issued commands into WSL. Direct process args and no automatic startup tasks reduce unexpected execution. No credentials, extensions, trust bypass or docker-group privilege was added. Only known version commands were executed.

## 10. Lessons learned and knowledge checks

1. Editing host and execution host can differ.
2. Process arguments avoid an extra shell parser.
3. A checked-in workspace need not expose personal editor config.
Knowledge check: did we verify Java debugging? No application exists for that yet. Unknown: later language-server/runtime integration needs.

## 11. Completion decision and handoff

IDE configuration acceptance is met by real workspace settings and executed process tasks, with GUI/Java-server limits disclosed. Only P1-022 is Done. Publish before P1-023 configures the Java formatter.
