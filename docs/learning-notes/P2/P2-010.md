## 1. Goal and context

Review how executors separate work submission from thread ownership, then make capacity/failure explicit. Future message handling needs bounded work and visible overload rather than silent drop or runaway memory.

## 2. Concepts explained in my own words

ExecutorService owns scheduling/lifecycle and may return Futures for completion. ThreadPoolExecutor first grows to core workers, then normally queues, then may grow toward maximum if the queue cannot accept work; saturation invokes a rejection policy. An unbounded queue can prevent maximumPoolSize from providing the intended bound. Fixed-thread convenience factories commonly have unbounded queues; cached pools can grow many threads.

AbortPolicy surfaces rejection. CallerRunsPolicy pushes work onto the caller and may impede an HTTP or Kafka polling thread; discard policies lose work unless deliberately accounted for. submit captures task failure in the Future, which must be observed. shutdown rejects new work and drains accepted work; shutdownNow attempts interruption and returns queued tasks without guaranteeing running code stops.

Virtual threads are task-per-thread concurrency for suitable waiting workloads, not faster CPU execution. Do not pool virtual threads merely to bound a downstream connection/service: apply admission limits to that resource. No virtual-thread or application pool is selected here.

## 3. Work performed and artifact

Ran a temporary single-worker/one-slot queue in WSL. Held running work with a latch, queued one task, observed excess rejection, released and joined accepted work, observed failed Future cause, then checked bounded termination and post-shutdown rejection.

## 4. Decisions and rationale

Use an explicit bounded ThreadPoolExecutor for the saturation demonstration; factory defaults would obscure queue limits. Prefer AbortPolicy over silent drop for evidence. Three-second waits are guard deadlines, not production budgets. Production sizing depends on workload and constrained dependencies; no architecture decision/ADR made.

## 5. Best practices and design patterns

Applies bounded resource ownership, explicit overload signaling and two-stage shutdown. Queueing alone is not end-to-end backpressure or durability. Kafka worker/offset coordination and application lifecycle wiring remain future tasks.

## 6. Common mistakes, errors and vulnerabilities

Observed overload and shutdown rejection and Future-carried task failure. Reviewed silent discard, unbounded queues/threads, nested same-pool blocking/starvation and forgotten Futures as risks. No induced system exhaustion or broker crash. Interrupting a task is not compensation for an external side effect.

## 7. Testing, verification and evidence

WSL release25/lint/Werror and assertions passed. The third task was rejected while one ran/one queued; accepted tasks completed; failed task cause was IllegalArgumentException; pool terminated and rejected new work. Exact bounded driver and output in evidence.

## 8. Debugging and operational notes

When a pool stalls, inspect active workers, queue capacity and tasks waiting on work scheduled to that same pool. Observe every submitted Future or explicit error path. Release gates and shut down owned executors in finally; do not rely on daemon threads to hide leaks.

## 9. Security and SSDLC check

Thread/queue bounds reduce local resource-exhaustion exposure but must align with downstream budgets and input limits. Use safe task identifiers, not credentials/payloads in names/logs. Synthetic pool has no external I/O. No production rate limiting or authorization installed.

## 10. Lessons learned and knowledge checks

Learned: queue type controls growth; bounded workers do not imply bounded pending work; submitted failures require observation; cancellation/shutdown is cooperative. Can explain why CallerRuns may be dangerous on a polling thread and why virtual threads do not expand database capacity. Next CompletableFuture composition.
