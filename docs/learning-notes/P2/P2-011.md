## 1. Goal and context

Review composition and terminal failure ownership before async client use. A returned future means a computation/result handle exists; what successful completion means depends on the adapter contract, not the class name.

## 2. Concepts explained in my own words

thenApply transforms a value; thenCompose flattens a returned stage. thenCombine combines dependent results; allOf waits for the group but does not return a typed list or automatically undo/cancel side effects. Non-async callbacks may execute on the completing/calling thread; async variants without an executor generally use the common pool. Deliberately choose where blocking or expensive work runs.

whenComplete observes success/failure without ordinary recovery; exceptionally replaces an exceptional result, and handle can map either outcome. Observers can themselves fail, so observe the final stage. get exposes checked waiting/interruption/failure exceptions; join uses unchecked completion wrapping and has no timeout overload.

Timed get limits the caller wait, not the computation. orTimeout completes its receiver exceptionally; dependent/shared consumers see that state. CompletableFuture.cancel does not promise worker interruption or external rollback. Distinguish response timeout, result cancellation and actual operation cancellation before retrying an unknown publication.

## 3. Work performed and artifact

Ran a temporary explicit bounded-executor chain yielding42, contrasted nested stages, inspected failed-stage cause/observer and intentional fallback. Tested wait timeout then later successful completion, exceptional stage timeout and cancelled-state retrieval. Pool shut down and terminated; no persistent async pipeline added.

## 4. Decisions and rationale

Use an owned explicit executor and bounded waits instead of relying on common-pool behavior or indefinite join. Use already-completed/failed futures for deterministic failure-path learning. Recovery sentinel is synthetic only. No architecture/ADR or application async contract selected.

## 5. Best practices and design patterns

Applies stage composition, terminal observation and lifecycle ownership. Failure observation differs from compensation/retry. Distributed idempotency, Kafka ack semantics and transactional rollback remain later work.

## 6. Common mistakes, errors and vulnerabilities

Observed failure propagation and cancellation/timeout states. Reviewed hidden final-stage failures, common-pool blocking, nested futures, callback context/MDC loss and retry after unknown outcome. Cancellation state was tested without underlying work, so no false interruption guarantee.

## 7. Testing, verification and evidence

WSL release25/lint/Werror and assertions passed: chain42, nested2, one observed failed cause, explicit fallback-1, wait-timeout then result7, orTimeout exceptional receiver and cancellation exception. Owned pool terminated. Exact bounded driver/output in evidence.

## 8. Debugging and operational notes

When completion hangs, inspect dependencies/executor saturation before adding blocking waits inside callbacks. Attach observers to the returned final stage. Determine whether a timeout mutated shared state or only ended a wait; preserve interruption separately. Avoid replacing any failure with successful null.

## 9. Security and SSDLC check

Timeouts do not revoke credentials, stop remote work or prevent duplicate external effects. Captured values/context can outlive a request and retain sensitive data. Exercise uses synthetic small values, no network, secrets or production threads. Resource budgets remain explicit future design.

## 10. Lessons learned and knowledge checks

Learned: compose flattens stages; callback execution is not always a new thread; observing differs from recovering; wait and stage timeouts differ; cancellation is not rollback. Can explain why retry after a publish timeout needs idempotency analysis. Next JVM memory/retention basics.
