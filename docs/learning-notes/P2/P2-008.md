## 1. Goal and context

Review failure as a caller contract instead of merely making the compiler happy. Kafka/client work later must distinguish invalid inputs, unknown outcomes and cancellation without converting them into success.

## 2. Concepts explained in my own words

Throwable contains Exception and Error branches. Checked exceptions require appropriate handling/declaration; RuntimeException subclasses and Errors are unchecked. Checked does not mean guaranteed recovery, and unchecked does not mean automatically transient or safe to ignore.

Choose a failure type for a meaningful boundary. Preserve cause when translating; do not wrap repeatedly or return null as success. try-with-resources retains a body failure and attaches close failures as suppressed exceptions. Error normally signals conditions outside ordinary recovery; catching Throwable to continue can conceal process failure.

InterruptedException often accompanies a cleared interrupt status. If not propagating it, restore the flag and stop/propagate cancellation at a useful boundary. Thread.interrupted() clears the current flag; isInterrupted() observes without clearing. Catching interruption must not initiate an unbounded retry. Future network timeouts may leave unknown side-effect outcomes and need idempotency analysis.

## 4. Decisions and rationale

Use existing JDK UncheckedIOException to demonstrate a meaningful translation without inventing a custom exception hierarchy. Keep the original IOException accessible. Use structured resource ownership over manual finally replacement. No architectural choice/ADR changed; project P1-029 standards remain controlling.

## 5. Best practices and design patterns

Applies exception translation, structured cleanup and cooperative cancellation. Handle where a recovery/reporting decision is possible; avoid log-and-rethrow at every layer. No retry/DLT pattern implemented or implied.

## 6. Common mistakes, errors and vulnerabilities

Observed original cause preserved, close failure suppressed and interrupted status restored. Compiler rejected IOException without declaration/handling. Broad catches, suppressed cancellation, sensitive exception text and retry storms remain reviewed risks; no live broker or security incident simulated.

## 7. Testing, verification and evidence

## 8. Debugging and operational notes

When cleanup obscures an error inspect getSuppressed as well as getCause. If shutdown hangs, inspect interrupt handling and resource ownership before retrying. A caller choosing to propagate InterruptedException need not blindly restore it at every layer; the restoration rule applies when the signal would otherwise be consumed.

## 9. Security and SSDLC check
