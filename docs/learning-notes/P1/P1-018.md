## 1. Goal and context

P1-018 installs a real Linux engine after P1-017 Maven verification, honoring the owner WSL runtime requirement. It does not start Kafka or a commerce stack; Compose and test execution are separate tasks.

## 2. Concepts explained in my own words

Docker has a client, privileged daemon and container runtimes. A working client version is weaker than reaching the server API. The Unix socket controls daemon access; docker-group access is effectively administrative. Ubuntu distribution packages differ from Docker CE upstream packages and should not be mixed.

## 3. Work performed and artifact

Added a pinned Ubuntu installer using a private signed index, installed Docker/containerd/runc, started/enabled systemd Docker and recorded ADR-0012. Checked actual client/server versions, socket endpoint, absence of Docker TCP listeners and unprivileged denial. No group or socket-permission shortcut was applied.

## 4. Decisions and rationale

Choose one maintained Ubuntu package family with recorded versions instead of adding another repository/key or Windows Docker Desktop. Use an isolated apt lists directory because an unrelated update owns the global lock. Rootless is a possible later reviewed alternative; no implicit privilege expansion is needed for these explicit root checks.

## 5. Best practices and design patterns

Authenticate apt metadata, pin primary packages, respect package locks, bound retries and preserve persistent state. Use explicit administrative access rather than chmod 666. Reproducible environment setup and least privilege are the relevant practices; no distributed application pattern is implemented.

## 6. Common mistakes, errors and vulnerabilities

The observed package-lock failure was diagnosed without killing its owner or deleting locks. Installation succeeded through a private index while normal dpkg protection remained. Non-root Docker access is observed denied; no TCP 2375/2376 listener was found. Rootful daemon/container escape risk remains and is not eliminated by local setup.

## 7. Testing, verification and evidence

Actual refreshed signed-index installation passed, then Linux daemon/package/socket/permission checks passed. The evidence preserves versions and executed commands. No container, Compose, broker or application test is claimed.

## 8. Debugging and operational notes

For API failure, distinguish inactive systemd service, wrong context and socket permission. Do not enable unauthenticated TCP or grant world access as a fix. Stop/disable/remove only after assessing real users/data; private apt work directories were scoped and cleaned.

## 9. Security and SSDLC check

Trust boundaries are signed distribution metadata into privileged packages and local client access to the rootful daemon. No new trust key, Docker group membership, exposed port or secret was added. Later Testcontainers/IDE permissions need explicit review; unprivileged usage is not promised.

## 10. Lessons learned and knowledge checks

1. Client and server availability are separate facts.
2. Package families must not be mixed.
3. A long-held apt lock does not authorize killing its owner.
4. Socket permissions are a privilege boundary.
Knowledge check: why avoid deleting Docker state on rollback? Future images/volumes may contain valued data. Unknown: image/container compatibility until P1-020.

## 11. Completion decision and handoff

Engine installation acceptance is met by actual API/package evidence and documented limitations/recovery. Only P1-018 is Done. Publish before P1-019 installs/verifies the matching Compose capability.
