## 1. Goal and context

P1-024 supplies observable static diagnostics after formatter setup. It uses the installed compiler to catch type/warning defects before future source enters the lab; P1-023 is Done and published.

## 2. Concepts explained in my own words

Static inspection examines source without running its business behavior. javac lint categories expose suspicious constructs; -Werror makes warning drift fail a check. Compilation is not equivalent to complete security analysis, and -proc:none prevents implicit annotation-processor execution for this probe.

## 3. Work performed and artifact

Added a validated-input lint script and baseline/limits document. Reviewed actual help-lint categories, ran warning-free source twice, and observed raw/unchecked warnings and malformed syntax rejected. Output went only to scoped temporary directories.

## 4. Decisions and rationale

Choose a zero-extra-dependency compiler baseline now; integrate it into builds later. Alternative: declare an untested IDE/SAST configuration complete; rejected because there is no application/build yet. Broader tools may be added at their owning tasks. No architecture ADR is needed for this local gate.

## 5. Best practices and design patterns

Use strict diagnostics, verify exact expected categories, isolate generated classes and prohibit hidden processors. Fix issues or justify narrow suppressions rather than disabling warnings wholesale. Fail-fast quality checks apply; no application design pattern is implemented.

## 6. Common mistakes, errors and vulnerabilities

Unchecked/raw collections can defer type errors to runtime; this defect is actually detected. A mere nonzero result could hide a missing-tool/config error, so the probe inspects expected diagnostics. Compiler lint still misses many security/domain issues and must not be marketed as SAST coverage.

## 7. Testing, verification and evidence

Two real clean compiles passed; raw/unchecked diagnostics plus Werror and syntax errors were observed rejected. Evidence preserves commands/assertions. No IDE inspection UI, security scanner, Maven build gate or application behavior was tested.

## 8. Debugging and operational notes

Check selected compiler/release first, then diagnostic category and source. Add explicit application classpaths only in future build work rather than weakening errors. Temporary bytecode is removed; rollback is a normal reviewed gate/config correction.

## 9. Security and SSDLC check

Boundary: developer source into compiler tooling. Existing file validation, absolute paths, disabled annotation processing and isolated outputs apply. No network artifacts, credentials or real payloads were introduced. Secret/dependency/data-flow scanning remains deferred.

## 10. Lessons learned and knowledge checks

1. Warnings can be enforceable evidence.
2. Expected diagnostic content is stronger than any failure status.
3. Compiler checks have explicit coverage limits.
Knowledge check: will this catch every swallowed exception? No. Unknown: broader analysis effectiveness on future application code.

## 11. Completion decision and handoff

Acceptance is met by configured diagnostics and repeated positive/negative outcomes. Only P1-024 is Done. Publish before P1-025 installs Kafka CLI tools without starting a broker.
