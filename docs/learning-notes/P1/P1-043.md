# P1-043 — Configure CI failure reporting

> Status: In Progress — hosted verification pending

## 1. Goal and context

Make CI failures discoverable and actionable, then demonstrate a real failure and restored success. Close only P1 after its environment and CI gate are verified; P2 is outside authorization.

## 2. Concepts explained in my own words

GitHub failure() runs a diagnostic step when earlier work failed. Writing Markdown to GITHUB_STEP_SUMMARY exposes recovery guidance without changing the failing job conclusion. A retained sanitized report provides status after console navigation; notification is not recovery itself.

## 4. Decisions and rationale

Use native Actions UI/annotation instead of outbound email/Slack integrations or write-scoped APIs. Inline reporting still works after checkout failure; upload remains checkout-dependent. Keep summary before upload so diagnostic copy is retained; later upload failure relies on native step reporting. Record these limits rather than promise universal delivery.

## 5. Best practices and design patterns

Apply observable failure, bounded diagnostics, data minimization and explicit recovery. Pipeline failure isolation applies; Kafka retry/DLQ patterns do not apply to this tooling task. No application security architecture implemented.

## 6. Common mistakes, errors and vulnerabilities

Swallowed/continue-on-error failures would yield false green; not used. Untrusted PR text in shell can inject commands; only fixed text and quoted trusted identifiers used. Raw reports can leak properties; existing sanitizer retained. Cancellation cannot guarantee reporting. Probe branch must not be merged.
