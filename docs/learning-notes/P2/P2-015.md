## 2. Concepts explained in my own words

Boot builds on the Spring context lifecycle but adds application startup milestones and availability. Refresh constructs/initializes relevant managed objects and starts auto-start lifecycle capabilities. The probe observes its bean's constructor, PostConstruct and SmartLifecycle start before ContextRefreshed/Started. A started event precedes startup runners; a runner can then fail. Only successful completion reaches Ready/accepting state and normal return. The JVM can outlive a closed context when non-daemon work remains, while forced process death can bypass context cleanup entirely.

The guide maps early environment/context events, bean-local callbacks, startup runners and coordinated lifecycle stop. These are different extension points, not interchangeable proof of readiness. Availability is logical state, not an installed HTTP health endpoint or automatic traffic router. In this non-web probe, close/stop/destruction did not emit REFUSING_TRAFFIC. Shutdown signaling and readiness withdrawal must be designed separately when future network/consumer capabilities appear.

## 5. Best practices and design patterns

Practices followed: consult official Boot4.2.0/Framework7.1.0/JDK25 references; keep source/POM/CI unchanged; observe only stable event/marker names; use Linux-only Java/Maven, temporary files, heap caps, explicit assertions, monotonic deadlines and child-process ownership. A static event observer illustrates the observer pattern; the context coordinates resource lifetime and lifecycle callbacks. There is no implemented publish/subscribe messaging, outbox, saga, idempotent consumer or dependency-injection service design.

Keep startup work finite, listener work short and shutdown completion bounded; never treat callback execution as crash durability. In future code, release owned resources, preserve interrupt semantics and signal real completion to SmartLifecycle's callback. No async worker, drain policy or phase timeout is implemented by this review.

## 6. Common mistakes, errors and vulnerabilities

| Risk / failure mode | Trigger | Observation or mitigation | Residual limit |
|---|---|---|---|
| Premature readiness | Treat started event as successful startup | Runner-failure probe reached Started then failed; no Ready/accepting state | Actual dependency readiness policy still absent. |
| Missing early events | Listener registered only as a bean | Pre-run listener observed Starting/environment events | Multiple/hierarchical contexts not tested. |
| Cleanup assumed after forced death | SIGKILL/process loss | Own JVM return-9 had no close/stop/destroy markers | No messaging durability or recovery established. |
| Close assumed to withdraw traffic | Non-web context closure | No REFUSING_TRAFFIC event observed; guide distinguishes context and availability | No server/platform routes traffic here. |
| Startup/shutdown hangs | Endless runner or forgotten async stop callback | Finite runner, instant marker stop and outer bounds; no real blocking worker | Actual async-stop timeout path not tested. |
| Partial startup resource leak | Failed refresh | Guide requires safe acquisition/release; tested runner failure cleanup only | Early refresh-failure teardown not simulated. |
| Wrong process signaled / secrets leaked | Broad process lookup or raw output | Signal only owned Popen process after marker; publish static traces only | Local WSL UID0 remains. |

No records, offsets, database state or authentication credentials were used, so data-loss/duplication/security-channel tests are not applicable. Those remain future Kafka/security tasks.

ContextClosedEvent precedes the observed stop/destroy markers; observing the event alone does not prove cleanup finished. ## 10. Lessons learned and knowledge checks

1. Process lifetime, context lifetime and bean lifetime can end at different times; a closed context does not kill arbitrary threads.
2. Started is before runners; the deliberately failed runner proved that readiness must be assessed later.
3. Bean initialization callbacks and coordinated lifecycle start/stop are separate responsibilities; one marker's ordering is not a universal bean graph guarantee.
4. SIGTERM cleanup was observed, but SIGKILL bypassed it. Crash recovery must survive missing callbacks.
5. Non-web closure did not publish readiness refusal; avoid importing server/platform assumptions into framework event observations.

Knowledge checks: Where must a listener be attached to see Starting? Which callback suits finite startup work? What must an async stop callback signal? Why can consumer data be duplicated even if PreDestroy exists? Why is readiness not a health endpoint here? Working conceptual/reproduction proficiency is demonstrated; multi-context ordering, real async drains, probe routing and Kafka shutdown semantics remain unverified.
