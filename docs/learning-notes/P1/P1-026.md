## 1. Goal and context

P1-026 ensures a native PostgreSQL client is ready for later persistence learning. P1-025 is Done/published. The task verifies the CLI, not a database server or application.

## 2. Concepts explained in my own words

psql is a client using libpq to connect to a database. Its local help/version can work without a server; a failed connection has a specific noninteractive exit status. Client version and server version are independent choices that need later compatibility evidence.

## 3. Work performed and artifact

Installed exact Ubuntu client/libpq packages and added installer/probe/guidance. Observed psql 16.15 and repeated help, then a bounded connection refusal on verified-unused loopback port 1. No PostgreSQL 16 server executable was installed.

## 4. Decisions and rationale

Use the current maintained Ubuntu client package instead of a Windows binary or a premature database container. Use a deliberately unavailable local endpoint for diagnostic verification, not a real account/production host. ADR-0006 remains the persistence decision; this does not set its server version.

## 5. Best practices and design patterns

Bound timeouts, disable startup scripts/prompts/credential files and use fake names. Assert the documented failure status/content rather than accepting any error. Separate dependency readiness from service availability. No persistence/application pattern is implemented.

## 6. Common mistakes, errors and vulnerabilities

A help/version check could be mislabeled a working database, inherited .psqlrc/password files could trigger unintended behavior, and an unbounded connection could hang. The probe explicitly isolates these inputs and expects a local refusal; no successful query or credential validation is claimed.

## 7. Testing, verification and evidence

Actual package/version, repeated help, refused-connection exit 2 and missing server binary checks passed. Evidence preserves exact arguments and outcomes. No database, TLS, JDBC, migration or recovery experiment ran.

## 8. Debugging and operational notes

If the client is missing, check the Linux package/path. If the local test port is occupied, abort rather than contacting that service. For real future failures, distinguish transport from authentication and inspect sanitized errors. No database-state rollback is required here.

## 9. Security and SSDLC check

The boundary is local CLI connection input. No real password, service file, user data or external host is used. PostgreSQL client startup files are disabled and prompting is forbidden. Runtime database security remains future P8/P9 work.

## 10. Lessons learned and knowledge checks

1. A database client does not imply a server.
2. Expected failure status is useful verification.
3. Startup/credential files are implicit inputs worth isolating.
Knowledge check: did SELECT 1 succeed? No connection was established. Unknown: later server/JDBC/TLS compatibility.

## 11. Completion decision and handoff

Acceptance is met by actual client installation and repeated/negative CLI evidence. Only P1-026 is Done. Publish before P1-027 defines package naming; no database deployment is authorized by this task.
