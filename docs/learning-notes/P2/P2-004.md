## 1. Goal and context

Review dependency inversion as control of source coupling, then distinguish it from the mechanics of passing collaborators. Important for future Kafka clients and testable application policy; no domain/infrastructure layers or Spring beans created.

## 2. Concepts explained in my own words

Dependency inversion keeps policy dependent on a suitable abstraction rather than a volatile implementation. Dependency injection is how an object receives a collaborator; it can inject a concrete class and still leave policy coupled to that class. Inversion of control is the broader shift in who creates/calls components.

In the exercise, DeadlinePolicy uses TickSource. FixedTicks and UnavailableTicks implement it. The small main method is the composition root that selects adapters. Runtime calls flow from policy to adapter; source dependencies point toward the contract. A service locator would hide lookup/configuration inside policy. Constructor injection exposes required collaborators and permits fail-fast validation; it does not make the collaborator itself immutable or thread-safe.

Do not leak KafkaProducer, transport exceptions or database entities into a future policy-owned contract simply while naming it an interface. Define delivery/failure/lifecycle promises at the appropriate learning milestone.

## 3. Work performed and artifact

Executed plain-Java constructor wiring in a temporary WSL directory. Tested before/at deadline, required-null rejection and visible adapter failure. Reviewed alternatives and source dependency arrows; no Spring dependency, module, service or port added to repository.

## 4. Decisions and rationale

Use an explicitly supplied narrow TickSource rather than a hidden static clock/service locator. This keeps the demonstration deterministic without mocking a framework. Prefer constructor validation over mutable field injection for mandatory collaborators. No significant new architecture choice; ADR-0002 remains controlling and formal service boundaries wait for later tasks.

## 5. Best practices and design patterns

Applies dependency inversion, composition root, constructor injection and fail-fast initialization in an isolated example. Do not introduce one interface per class or an abstract-factory framework without need. Spring wiring is deferred to P2-016, so this review makes no claim of configured DI.

## 6. Common mistakes, errors and vulnerabilities

Service-locator/global lookups hide dependencies and can make tests environment dependent. Null collaborator rejection and infrastructure failure propagation were actually observed. Circular dependencies are a design smell to revisit, not a reason to add field injection automatically; no Spring cycle experiment executed.

## 7. Testing, verification and evidence

WSL javac release25/lint/Werror and assertions passed. Policy results changed only through supplied TickSource; null was rejected and IllegalStateException propagated. Exact source/driver/output in evidence. Source-graph review was self-review; no independent or framework integration test.

## 8. Debugging and operational notes

If a unit test needs network or container setup, inspect whether the policy constructs a concrete adapter internally. Wire at a visible composition root and test contract failures explicitly. Production wall-clock timestamps differ from monotonic elapsed-time budgets; the numeric probe does not solve that future issue.

## 9. Security and SSDLC check

No authority is reduced merely by using an interface. Credentials, network access and resource shutdown belong in deliberately owned adapters; failure must not be converted to apparent success. Current exercise has no secrets, I/O adapter or network. No authorization controls claimed.

## 10. Lessons learned and knowledge checks

Learned: DI can exist without DIP; runtime call direction differs from source dependency direction; explicit required construction prevents partially initialized use; fake adapters must propagate meaningful failures. Can explain composition root versus service locator. Next collections/generics to make data contracts type-safe.
