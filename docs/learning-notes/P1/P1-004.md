## 1. Goal and context

Consistent editing reduces irrelevant diffs while the lab grows into Java, YAML and documentation. P1-003 is Done and published. This task configures editing hints and explains their scope; it does not install an IDE or select a Java formatter.

## 2. Concepts explained in my own words

EditorConfig searches parent directories until root=true, then applies matching sections in order. Properties guide editors with support; Git attributes separately control committed/checked-out text. A CRLF working-copy ledger can therefore coexist with LF normalization in Git. Neither mechanism validates Kafka behavior or program correctness.

## 3. Work performed and artifact

Added comments and explicit Markdown, CSV and Windows-script rules; retained 2-space defaults, 4-space Java and 2-space XML/POM. Added editor-settings guidance explaining precedence, Git differences, observed LF-to-CRLF warnings and recovery. No existing source or roadmap files were bulk-formatted.

## 4. Decisions and rationale

Preserve CSV CRLF and significant cell whitespace because that is the inherited working-copy baseline. Alternative: global LF normalization; rejected as unrelated destructive churn. Trim new Markdown trailing whitespace to align with git diff --check; prefer paragraph structure over hard-break spaces. Keep global Git settings unchanged. No architecture ADR is required.

## 5. Best practices and design patterns

Use versioned repository defaults rather than undocumented personal settings. Document intentional exceptions and separate formatting hints from enforcement. This is configuration layering, not an application design pattern. Actual formatter/inspection selection remains P1-023/P1-024/P1-035.

## 6. Common mistakes, errors and vulnerabilities

A save-all operation could rewrite the ledger or historical Markdown. The task changes declarations only and preserves originals. The previous Markdown no-trim rule conflicted with the staged whitespace gate for new work; trimming removes that invitation. Unsupported editors can ignore hints; this risk is explicitly unverified rather than hidden.

## 7. Testing, verification and evidence

Executed configparser-based static syntax/property checks, byte checks and git check-attr. Java/XML/Markdown/CSV/CMD declarations match policy; Git Markdown eol is LF and CSV eol remains unspecified. No genuine core-resolution or IDE experiment ran because the core is not installed; the evidence labels this limitation.

## 8. Debugging and operational notes

For unexpected whitespace, inspect editor support and closer .editorconfig files before altering global Git configuration. The observed .gitignore LF-to-CRLF warning comes from unspecified Git eol, not a failed EditorConfig check. Revert configuration with a new commit and review unrelated save-generated diffs individually.

## 9. Security and SSDLC check

The protected asset is reviewable, accurate source/evidence. UTF-8 without BOM avoids gratuitous ledger encoding drift; no credentials or new dependencies were added. EditorConfig does not prevent secrets, malicious code or unsafe Kafka configuration. Content review and future scanning remain necessary.

## 10. Lessons learned and knowledge checks

1. Editor hints and Git normalization operate at different layers.
2. CSV cell spaces and row endings deserve an explicit exception.
3. root=true limits inherited personal settings.
4. Static declaration validation is weaker than observing an IDE save.
