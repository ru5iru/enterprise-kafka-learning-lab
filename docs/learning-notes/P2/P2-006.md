## 1. Goal and context

Review functional transformations and their limits before immutable values and concurrent tasks. Java streams operate on local values; they are unrelated to Kafka Streams topology or broker delivery.

## 2. Concepts explained in my own words

A lambda supplies behavior for a target functional interface; a method reference is a compatible shorthand. Captured local variables must be final/effectively final, but a captured object can remain mutable. A stream connects a source, intermediate operations and a terminal result. It stores a processing description, not a reusable collection.

Use pure map/filter/collect-style transformations when intent is clearer than a loop. Reduction needs associative combination and a valid identity for parallel regrouping; subtraction is a poor parallel reduction. Avoid using peek/map for required auditing or persistence because traversal/optimization may skip incidental side effects. Close I/O-backed streams with try-with-resources; collection streams need no such external resource ownership.

Stateful sorting/distinct and unbounded collection can consume large memory. parallelStream does not make shared mutation safe or preserve completion order of side effects. Prefer sequential execution unless measured independent work justifies deliberate executor/resource design.

## 4. Decisions and rationale

Use toList traversal for the laziness observation instead of count, whose optimization can bypass intermediate work. A tiny mutable counter is restricted to diagnostic sequential code; production examples use pure transformation/reduction. Loops remain preferable for complex control flow or explicit failure handling. No architecture/ADR change.

## 5. Best practices and design patterns

Applies functional pipeline and associative reduction concepts. Avoid hidden effects, parallel blocking I/O and automatic parallelization. Kafka Streams and async execution remain separate future learning, not inferred from java.util.stream.

## 6. Common mistakes, errors and vulnerabilities

Consumed-stream reuse and bad parse were executed failures; effectively-final violation was a compile rejection. Shared mutable accumulators, unbounded streams and file leaks are reviewed risks only. A list result preserving encounter order does not prove ordered side effects or cross-partition event order.

## 7. Testing, verification and evidence

WSL release25/lint/Werror compilation and assertions passed. Observed lazy/eager boundary, [10,30], sum6 for both traversals and expected exceptions; invalid capture rejected. Exact driver/output in evidence. No performance claim or application test.

## 8. Debugging and operational notes

If a callback seems not to run, inspect terminal operation, short-circuiting and legal optimization before adding side effects. Recreate a stream from its source rather than reuse a consumed instance. Explicitly inspect where exceptions surface: here during the terminal operation.

## 9. Security and SSDLC check

Bound inputs and retained output before applying stream transformations to untrusted data. Do not log payloads inside callbacks or treat a parallel stream as resource isolation. Exercise uses only small synthetic values, no files/network/secrets. No new runtime control introduced.

## 10. Lessons learned and knowledge checks

Learned: laziness delays work; final capture does not freeze objects; reduction must survive regrouping; side effects are poor pipeline contracts. Can distinguish Java streams from Kafka Streams and explain why peek is not a durable audit mechanism. Next records and defensive copying.
