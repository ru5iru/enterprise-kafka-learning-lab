## 1. Goal and context

Issue templates turn work requests into scoped learning tasks or reproducible defects. P1-007 is Done and pushed. The task is repository configuration, not creating issues, assigning people or adding business features.

## 2. Concepts explained in my own words

Legacy Markdown issue templates use YAML front matter to populate the chooser and editable body prompts to guide reporting. config.yml controls chooser options and contact routes. Those prompts are not required-field validation, and issue closure does not update the canonical task CSV.

## 3. Work performed and artifact

Corrected the task template metadata from description to about, expanded task/dependency/design/verification fields, added a separate sanitized defect template and configured the chooser with a security-policy contact link. Labels and assignees stay empty; no person is notified.

## 4. Decisions and rationale

Choose Markdown rather than YAML issue forms because the existing workflow is document driven and needs editable nuanced evidence. Forms could enforce fields, but add schema/tooling complexity and still cannot guarantee truth or sanitization. Disable ordinary blank chooser submissions to encourage templates, while documenting bypass limitations. No ADR is needed for this template choice.

## 5. Best practices and design patterns

Separate expected behavior from observed behavior and planned verification from executed results. Require existing task IDs without inventing new roadmap entries. Route sensitive reports to policy rather than requesting raw logs. This is structured intake, not a runtime design pattern; server validation is not claimed.

## 6. Common mistakes, errors and vulnerabilities

The previous description key was inappropriate for a Markdown template front matter; it is now about. Self-review also corrected relative links that could resolve incorrectly after copying the body into an issue; explicit repository URLs now retain the target context. Other risks include auto-applying missing labels, auto-assigning people, public token dumps and blank required evidence. Static checks cover metadata/links and prompts; they cannot prevent a reporter deleting instructions or using the API.

## 7. Testing, verification and evidence

Executed metadata key/value, distinct-name, chooser shape, local-link and field-coverage checks. Positive walkthroughs covered a task and a bug; the negative sensitive-report scenario follows SECURITY.md. No real issue submission, GitHub chooser render or general YAML validator ran; templates are not live until default-branch merge.

## 8. Debugging and operational notes

If a template is absent after merge, inspect path/case, front matter name/about and whether the commit is on default main. For incomplete reports, request missing sanitized evidence rather than guessing. Revert/configure chooser with a normal commit; do not publish sensitive sample reports for testing.

## 9. Security and SSDLC check

The trust boundary is reporter content entering public issue history. No raw environments, credentials, customer data or exploit details are requested. The contact link points to policy and does not claim a private advisory channel is enabled. P1-010 verifies and documents the actual reporting options.

## 10. Lessons learned and knowledge checks

1. Markdown templates and YAML forms use different metadata.
2. Chooser guidance does not enforce all submission paths.
3. Task IDs and CSV status remain authoritative.
4. Sanitized expected/actual evidence is more useful than a full environment dump.
Knowledge check: does checking issue boxes make a task Done? No. Unknown: GitHub rendered discovery until merge.
