## 1. Goal and context

P1-014 selects the JDK installed by P1-013 without changing the Windows workstation. It prepares repeatable WSL command execution; compiling Java belongs to P1-015.

## 2. Concepts explained in my own words

JAVA_HOME identifies a JDK directory, while PATH chooses executables. They can disagree. A project launcher makes both explicit and excludes inherited Windows entries so a Linux build cannot accidentally invoke Windows Maven. Environment inheritance is scoped to the launched process tree.

## 3. Work performed and artifact

Added environment.sh and lab.sh, plus usage/recovery guidance. The launcher resolves its own directory, selects the Linux JDK, changes to repo root and execs the requested argument vector. Verified positive runtime selection and two rejected configurations.

## 4. Decisions and rationale

Choose explicit project activation over editing .bashrc/global Windows variables, preserving other projects. Alternative: rely on whichever java is first in inherited PATH; rejected after observing Windows Maven leakage. ADR-0011 supplies the environment decision; no new ADR is needed.

## 5. Best practices and design patterns

Validate configuration before execution, quote paths and pass arguments without eval. Return the child status rather than swallowing failures. Process-local configuration is the applicable pattern; no Kafka runtime behavior is implemented.

## 6. Common mistakes, errors and vulnerabilities

Wrong/missing JAVA_HOME can make Maven fail or use another JDK. An invalid LAB_JAVA_HOME is observed rejected. Calling the launcher with no command returns 64. A different explicit override still requires version review; existence alone cannot prove compatibility.

## 7. Testing, verification and evidence

The evidence script executed in Ubuntu, asserted exact JAVA_HOME/java path, ran java --version, and checked invalid-home and no-command failures. All passed. No compiler/build/IDE test was claimed.

## 8. Debugging and operational notes

If java differs outside the launcher, inspect command resolution rather than installing another Windows JDK. For Invalid Linux JDK, verify the versioned path and installation. Stop using the launcher to roll back; no login-file edits exist.

## 9. Security and SSDLC check

The boundary is Windows environment inheritance into Linux build commands. A controlled PATH, validated JDK and direct exec reduce ambiguity/injection risk. No secret variables are printed or persisted; configuration values are public tool paths only.

## 10. Lessons learned and knowledge checks

1. JAVA_HOME and PATH have separate responsibilities.
2. Explicit activation avoids global side effects.
3. Direct argument passing avoids eval injection.
Knowledge check: does arbitrary WSL bash now use this JDK automatically? No; use the launcher/source. Unknown: Maven behavior until its install task.

## 11. Completion decision and handoff

JAVA_HOME setup acceptance is met by observed selection/rejection and documented rollback. Only P1-014 is Done with evidence. Publish before P1-015, which will verify actual compilation.
