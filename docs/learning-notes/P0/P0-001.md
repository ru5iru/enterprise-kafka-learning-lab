## 2. Concepts explained in my own words

A project objective describes an outcome the project should produce. A learner competency describes something a person should be able to explain or do; a requirement constrains system behavior; an acceptance criterion defines how a result will be judged. Confusing these layers would prematurely prescribe later P0 work. For example, OBJ-06 asks for defensible capacity conclusions, while events per second and latency thresholds still require workload modeling.

An event is a record of something that happened. A producer writes events to Kafka, topics organize those events, and consumers read them. This separation makes a simple simulation useful for studying asynchronous behavior, but a successful write/read alone does not prove downstream processing correctness. The [Apache introduction](https://kafka.apache.org/intro/) supplies this conceptual basis. The charter therefore connects later reliability and observability work to evidence rather than promising an untested guarantee.

The invariant for this task is documentary: every objective has a rationale, an implication, and a roadmap connection, while no planned capability is presented as deployed. The current task has no new runtime message flow to diagram; the existing conceptual architecture remains unchanged.

## 5. Best practices and design patterns

Applied outcome-to-evidence traceability, explicit assumptions, incremental delivery, small changes, authoritative tracking, and early SSDLC review. Keeping objective, rationale, and consequence together makes later proposals easier to assess. Distinguishing a hypothesis from measured capacity prevents a planning number becoming a false benchmark.

No runtime software design pattern was implemented. Publish/subscribe is conceptual motivation for the lab, not a new implementation here. Idempotent consumers, retry topologies, Outbox, and Saga mechanisms belong to later reliability/persistence experiments; naming them would not prove them. Production tuning, runtime threat testing, and release gates remain deferred until the corresponding systems exist.

## 10. Lessons learned and knowledge checks

- A phase-level deliverable can span many tasks; a row's precise acceptance criterion governs the current increment.
- An objective becomes more useful when its consequence and eventual evidence are explicit, even before numeric requirements exist.
- User count alone leaves concurrency, event rate, payload size, retention, and capacity unanswered.
- Progressive security requires disclosure from the first planning document; intended controls do not protect anything yet.
- Documentation-only work can have reproducible verification without inventing integration tests.
