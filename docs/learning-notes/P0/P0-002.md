## 2. Concepts explained in my own words

A project objective describes the value the lab should produce; a learning objective describes what its learner should be able to explain or demonstrate. A proficiency rubric tells us what evidence distinguishes recognition of a term from independent application or diagnosis. For example, OBJ-03 seeks demonstrable correctness trade-offs. LO-05 turns that into a learner who can predict commit/crash windows, account for records and side effects, and explain the limits of transaction guarantees.

The three cumulative levels are Explain (L1), Apply independently (L2), and Diagnose and evaluate (L3). Reading documentation is allowed at every level; independence means the learner can reproduce and justify the result rather than copy an unexplained recipe. These are local assessment definitions, not a validated external taxonomy, certification, or statement that the learner is already proficient.

An experiment needs a predicted observation, controlled change, actual evidence, and interpretation. Observing a duplicate after a crash can be expected behavior; diagnosing why it occurred can demonstrate learning. Conversely, a working message flow cannot establish exactly-once external business effects. The distinction between Kafka transaction scope and external effects motivates separate reliability and database-consistency objectives, informed by [Spring Kafka EOS](https://docs.spring.io/spring-kafka/reference/kafka/exactly-once.html) and [PostgreSQL logical decoding](https://www.postgresql.org/docs/current/logicaldecoding-explanation.html).

The documentary invariant is that every LO has all requested fields and traces to an existing charter objective and roadmap phase. Learner attainment stays not assessed until future task evidence supports it. No message flow or runtime topology changed, so no new diagram is warranted.

## 10. Lessons learned and knowledge checks

- Project outcomes become assessable learning only when actions, experiments, evidence, and target proficiency are connected.
- Defining a competency does not demonstrate it; task completion and learner attainment need separate claims.
- A negative result can show understanding when the learner predicts and explains it; merely causing a failure does not establish diagnostic proficiency.
- Kafka transaction scope, external side effects, and database capture/replay need distinct questions and evidence.
- Grouping the roadmap avoids duplicating the task ledger while preserving dependencies and the native-to-framework progression.

Questions now answerable: What evidence distinguishes applying a recipe from diagnosing a fault? How does each charter objective connect to learner work? Why does learning security require denied as well as allowed cases? Why is capacity modeling different from declaring a user count?

Still unknown: the learner's starting proficiency, actual experiment outcomes, compatible software versions, workload values, hardware limits, detailed scope, and eventual service objectives. The rubric supports future assessment without inventing a diagnostic pre-test or learning schedule now.
