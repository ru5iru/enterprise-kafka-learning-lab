## 1. Goal and context

Conventional messages make one task commit understandable without reading the conversation. P1-005 is Done and pushed. This task defines history semantics; it does not create a release pipeline or modify Kafka contracts.

## 2. Concepts explained in my own words

The type summarizes intent, scope locates the affected concern, description states the change and footers carry metadata. feat/fix have release semantics under the specification, while other types are allowed. Task references are a local traceability requirement, not part of the public specification. Breaking markers describe incompatibility, not importance.

## 3. Work performed and artifact

Expanded the existing Conventional Commits section with type choices, optional scope/body, imperative local wording, task footer requirements, real breaking-change meaning, hypothetical examples, rejection examples and non-destructive corrections. Reused the established examples and checked the five published P1 predecessor messages.

## 4. Decisions and rationale

Use docs for this policy instead of feat, because no application capability appears. Alternative: require a complex parser/release tool now; rejected because P1-006 is a documentation decision and builds do not exist. Keep roughly 72 characters as guidance rather than pretending the spec mandates it. No new architecture ADR is required.

## 5. Best practices and design patterns

Explain motivation in a body when useful and link the exact task in a footer. Preserve shared history and label hypothetical contract examples. Semantic traceability is the relevant practice; no runtime design pattern applies. Automated validation/versioning remains deferred.

## 6. Common mistakes, errors and vulnerabilities

A fabricated issue footer can accidentally close an unrelated issue; use task refs without invented issue numbers. Calling all work feat or all changes breaking misleads release tooling. Secrets in commit messages survive file deletion. These were reviewed failure modes; no release or secret incident was claimed.

## 7. Testing, verification and evidence

The verifier checked documented semantics, local/spec distinctions, breaking/revert coverage, actual CSV existence for example IDs and five published predecessor messages. Self-review rejected unstructured/empty subjects and missing local references. No full parser or commitlint was run; exact checks and output are in evidence.

## 8. Debugging and operational notes

If a message is rejected in review, identify whether the rule comes from the public spec or repository policy. Inspect git log and the staged diff before writing a correction. After push, prefer follow-up/revert explanation over rewriting a shared branch.

## 9. Security and SSDLC check

The assets are trustworthy shared history and task traceability. Messages must avoid secrets, private URLs and personal data. No hooks, network permissions or runtime controls were added. Later CI may enforce documented rules after an explicit implementation task.

## 10. Lessons learned and knowledge checks

1. Task completion is not automatically a feature.
2. Local Refs and subject-length guidance extend the public spec.
3. Breaking markers need an actual compatibility consequence.
4. Published history should not be rewritten for cosmetics.
Knowledge check: can a docs commit be Conventional without a scope? Yes under the spec; task refs still apply locally. Unknown: future release tooling.
