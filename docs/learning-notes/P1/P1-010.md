## 1. Goal and context

SECURITY.md must tell a contributor where to report without inventing a contact or pretending planned controls exist. P1-009 is Done and pushed. The task is an accurate discoverable policy; it does not enable reporting features, certify security or execute incident response.

## 2. Concepts explained in my own words

A security policy communicates scope and process; private reporting is a separate platform capability. A public contact request may ask how to reach the owner, but must not carry sensitive findings. Removing a token from the current tree is different from invalidating it or removing historical copies.

## 3. Work performed and artifact

Replaced the vague policy with supported-scope limits, dated API observations, private-route fallback, minimal private-report contents, credential-exposure response and deferred controls. API read confirmed private reporting disabled and zero published releases. No report, contact message or remote setting was created.

## 4. Decisions and rationale

Describe real unavailable-channel behavior instead of fabricating an email or enabling a feature while writing a document. Alternative: simply say report privately without explaining how; rejected because the checked repository has no designated route. Use GitHub recommended non-sensitive contact request if needed, and wait before sharing details. This clarifies existing SSDLC policy without a new architecture/security mechanism; no ADR is necessary.

## 5. Best practices and design patterns

Limit sensitive information to a verified private channel; use synthetic reproduction and minimum necessary evidence. Distinguish support intentions from a response SLA. Preserve truthful dated observations and label future controls. Coordinated disclosure is the process pattern, not a deployed authentication/authorization control.

## 6. Common mistakes, errors and vulnerabilities

A reporter could mistake public issues for a private channel, infer an unmonitored email from author data, or post secrets to prove a leak. The policy explicitly rejects those actions. Disabled private reporting and no designated contact are observed limitations, not repaired controls. Token revocation remains necessary after a real leak; none occurred in this task.

## 7. Testing, verification and evidence

Actual API reads returned enabled=false and zero published releases. The static verifier checked policy sections, safe fallback, absence of an invented email, local targets and planning-only security disclosure. Two old reference URLs failed; official current pages were found by search before final references were written. No actual private report or incident experiment ran.

## 8. Debugging and operational notes

If the reporting button is absent, follow the no-details contact-request route rather than retrying with public exploit data. Verify any offered private route before sending the report. Recheck date-sensitive settings after changes. Revert policy text normally; no Git/security feature rollback is needed because no setting changed.

## 9. Security and SSDLC check

The trust boundary is public repository discussion versus private vulnerability information. Policy minimizes exposure and discloses the unavailable private feature. Credential use for API reads stayed in memory and output was restricted to boolean/release count. Runtime security, secret scanning and platform reporting enforcement remain unimplemented/unverified.

## 10. Lessons learned and knowledge checks

1. A SECURITY.md file does not enable private reporting.
2. A safe fallback can request contact without disclosing a finding.
3. No releases means no honest release-support matrix yet.
4. Removing a secret is not credential revocation.
Knowledge check: what may go in a public contact request? Only the request for a private route. Unknown: owner-selected monitored contact and future feature enablement.
