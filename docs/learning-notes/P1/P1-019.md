## 1. Goal and context

P1-019 verifies Compose after P1-018 engine installation. The plugin was absent, so installing the selected matching Ubuntu plugin was necessary to perform the verification. No lab stack is introduced.

## 2. Concepts explained in my own words

Compose parses a declarative model and interpolates configuration before resource creation. A config check does not start containers or prove readiness. Required variables can fail early; schema errors should stop before deployment. Daemon listing is a separate API access check.

## 3. Work performed and artifact

Installed pinned Ubuntu Compose v2, added a temporary config/failure probe and usage/limits guide. Two config passes succeeded; missing required input and an invalid schema failed. The project-list API succeeded under explicit root access; no stack/image pull ran.

## 4. Decisions and rationale

Use config-only synthetic fixtures rather than a permanent Compose stack before P3. Retain Ubuntu package-family consistency instead of mixing upstream/legacy docker-compose. Use /dev/null env file to isolate inputs and quiet output to avoid value leakage. ADR-0012 already governs runtime access.

## 5. Best practices and design patterns

Validate configuration before execution, test required-input failures and keep fake data isolated. Separate parsing from daemon access and runtime readiness. Fail-fast configuration is the applicable pattern; no publish/subscribe service exists yet.

## 6. Common mistakes, errors and vulnerabilities

A valid YAML file may still violate Compose schema, and missing variables may otherwise become empty settings. These negative cases are observed rejected. Implicit .env loading and config output could reveal secrets; explicit empty env-file/fake values/quiet mode avoid them here. Runtime integration remains unverified.

## 7. Testing, verification and evidence

The executed script reports installed plugin version, two positive config validations, two expected failures and a successful daemon API list. No browser/UI, Kafka, network or running Compose integration test is claimed.

## 8. Debugging and operational notes

Distinguish parser/interpolation errors from daemon permissions. Review the first relevant error instead of making the socket world-writable. Temporary config/log files are removed; package rollback requires consumer review and no volume purge.

## 9. Security and SSDLC check

The boundaries are configuration input and privileged daemon access. Only synthetic values/reserved image names are used; no network image request or published port exists. The plugin is signed Ubuntu packaging, while comprehensive host patch/scanner coverage is explicitly not claimed.

## 10. Lessons learned and knowledge checks

1. config validation is distinct from deployment.
2. Required interpolation catches missing settings early.
3. Empty explicit env files improve isolation.
Knowledge check: does Compose ls prove a service is ready? No. Unknown: container execution until P1-020.

Acceptance is met by real repeated CLI/failure/API evidence and disclosed limits. Only P1-019 is Done. Publish before P1-020 runs a bounded image/container experiment.
