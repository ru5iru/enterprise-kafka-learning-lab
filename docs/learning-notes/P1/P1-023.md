## 1. Goal and context

P1-023 configures deterministic Java formatting in WSL after P1-022 editor integration. There are no services to reformat yet; verification uses temporary synthetic source only.

## 2. Concepts explained in my own words

A formatter parses source and emits a canonical layout, while a check compares intended layout without writing. Idempotence means a second formatting pass leaves identical bytes. Source layout/import handling is different from semantic correctness or a compiler/static-analysis result.

## 3. Work performed and artifact

Installed publisher-pinned Google Java Format 2.0.0, added explicit check/write wrapper and style guidance. Real synthetic tests observed drift rejection, write success, four-space AOSP output, byte-identical repeat, clean pass and malformed-source rejection.

## 4. Decisions and rationale

Choose AOSP mode to match the established four-space Java indentation. Alternative: editor-specific formatting or Google two-space default; rejected to avoid cross-host drift/conflict with EditorConfig. Use a CLI now and configure build enforcement only in P1-035. This is development convention, not a new architecture ADR.

## 5. Best practices and design patterns

Pin formatter bytes/version/style, default to explicit check/write modes and review diffs. Convert input paths to absolute names to avoid option/@file interpretation. Deterministic tooling is the relevant pattern; no runtime application pattern is involved.

## 6. Common mistakes, errors and vulnerabilities

An unpinned formatter update can create unrelated diffs, malformed source cannot be safely formatted, and option-like filenames could change CLI behavior. Explicit pins, existing .java validation and absolute paths address these risks. Import/comment changes still require review and tests.

## 7. Testing, verification and evidence

The exact installer checksum and actual Java 25 CLI were exercised. Evidence runs synthetic positive/negative/idempotence checks and records results. No Java service, IDE formatting UI or Maven formatter integration was claimed.

## 8. Debugging and operational notes

For formatting drift, inspect the diff and invoke --write deliberately. For parse errors, fix the source rather than skipping checks. For tool mismatch, verify the installed JAR/hash and Java environment. Roll back through reviewed source/pin correction, not mass rewrite.

## 9. Security and SSDLC check

The dependency is a publisher Java executable installed only inside WSL. Verified TLS/hash, fixed version, bounded explicit inputs and no automatic editor execution apply. No secrets or real customer source payloads were used; no vulnerability scan was run.

## 10. Lessons learned and knowledge checks

1. Check and write modes serve different purposes.
2. Idempotence is observable.
3. Formatter style must agree with the repository convention.
4. Source formatting is not semantic verification.
Knowledge check: does a clean format prove a unit test passes? No. Unknown: build integration until P1-035.

## 11. Completion decision and handoff

Acceptance is met by configured executable style and observed positive/failure behavior. Only P1-023 is Done. Publish before P1-024 configures static inspections.
