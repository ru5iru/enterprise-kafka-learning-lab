## 1. Goal and context

P1-001 establishes the shared source/evidence location for the Kafka lab. An existing remote is a valid deliverable when verified; this task does not recreate it or deploy Kafka. P0-GATE was checked against all 45 Done rows, the phase review and the owner-requested merge.

## 2. Concepts explained in my own words

A local Git repository stores commits; origin names a remote; GitHub hosts the collaborative copy. The default branch is a remote setting, not whichever topic branch is checked out locally. One monorepo supports coordinated experiment history while service builds remain independent under ADR-0002.

## 3. Work performed and artifact

Added the repository baseline with observed visibility, default branch, protection, issues, P0 merge and recovery. Read GitHub API metadata and used Git CLI to verify remote HEAD/main. No remote setting changed. The accumulated P1 work uses sequential stacked task branches, each published before the next begins.

## 4. Decisions and rationale

Adopt the existing repository because it already contains the accepted P0 history. Alternative: create a new repository, which would split evidence and require migration for no learning benefit. Keep existing public visibility and disclose it rather than silently changing access. ADR-0002 already governs the architecture; no new architecture decision is needed.

## 5. Best practices and design patterns

Treat verification as idempotent adoption: observing an existing resource avoids duplicate creation. Keep task evidence next to source and verify the remote rather than trusting a local name. Publish focused task commits. No application design pattern is implemented; protected-branch enforcement and CI remain absent.

## 6. Common mistakes, errors and vulnerabilities

An origin alias could point to the wrong host or include a token; exact URL checking avoids that risk. A local main can be stale, so verify remote refs. Public visibility makes accidental secret publication consequential. These are reviewed failure modes; no authentication outage or secret incident was manufactured.

## 7. Testing, verification and evidence

The CLI verifier in the linked evidence passed: exact origin URL, default remote HEAD, P0 main SHA and planning-only boundary. API metadata was also inspected. Shared ledger, link and staging gates run before publication. No unit/integration/broker test applies to repository adoption.

## 8. Debugging and operational notes

If a remote read fails, distinguish network/access errors from repository absence. Inspect only sanitized URL/ref output and retry after resolving access. Correct documentary errors with a new commit; do not recreate the remote, delete branches or force-push.

## 9. Security and SSDLC check

The trust boundary is workstation credential manager to GitHub. Existing credentials were consumed in memory without printing them; no credentials enter the baseline. Main protection is observed absent, so review is a procedural control only. Full security scanning remains later work.

## 10. Lessons learned and knowledge checks

1. Creation tasks can be satisfied by verified existing resources.
2. Remote HEAD and local checkout are different concepts.
3. A monorepo does not require coupled service builds.
4. Publishing task branches is not a merge to main.
